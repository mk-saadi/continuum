# Subagent execution budgets and results

Phases 1–3 implemented on 2026-10-13. Historical evidence artifacts remain unchanged. Phase 3 adds parent delegation guidance and accounting visibility without changing runtime budget or compaction policy.

## Settings

Settings → General → Sub-agent execution budgets uses the existing `subagentBudgets` app-setting, IPC get/save handlers, and preload API. Old records need no manual migration: missing fields normalize to null. Automatic ignores stored custom values; switching modes preserves them. In Custom, each null/blank field independently uses Automatic. Settings are resolved once per new child; editing settings, sending a message, resuming, retrying, or changing the current model never refills a live child's ledger.

| Setting | Allowed custom values | Automatic |
| --- | --- | --- |
| `maxToolCalls` | null or integer 1–100 | Investigation 10; file analysis 32 file reads; web extraction 1 page fetch |
| `maxTurns` | null or integer 1–100 | Investigation 8 total model requests; file/web 2 |
| `maxAggregateToolCalls` | null or integer 1–10000 | 40 child tool dispatches per parent invocation |
| `maxInputTokens` | null or integer 512–1000000 | 4 × resolved child context window |
| `maxOutputTokens` | null or integer 256–500000 | Resolved request limit × task-kind request ceiling |

Per-request output ceilings remain 2048 investigation / 3072 file / 1024 web. Automatic output derives from the configured request limit when Custom overrides turns but leaves output blank; this derivation applies only at child creation and is displayed through the existing policy API. Custom input/output fields remain independent limits. Increasing tool calls alone does not increase requests, input tokens or output tokens. Explicit internal runtime `maxTurns`/`maxToolCalls` options remain initial overrides; they never override an existing child's state.

File/web remain specialized, tool-free model tasks with at most one empty-answer retry (two attempts), even if Custom's request upper bound is larger. A lower configured turn limit restricts them. Increasing their turn upper bound does not introduce new retries or autonomous tools. File payload caps now use the same conservative byte/3 sizing as request admission, retaining truncate-and-continue, UTF-8 checks, path restrictions, and file order. HTTP/fetch, empty-page and file validation failures remain distinguishable. No model backend, cloud provider record, parent sampling, permission policy or model-selection behavior was replaced.

The ten-call/eight-request Automatic investigation policy is retained for compatibility because the nine Phase 0 live runs are still unavailable. Forty aggregate calls accommodates four default investigation children (the fixed broad task), while preventing unlimited child spawning from bypassing per-child bounds. This is a conservative design default, not an empirically optimized number. Evaluate the documented 50-call candidate with Custom `maxToolCalls:50`, an explicit sufficient request limit (e.g. 30), and `maxAggregateToolCalls` large enough for the planned children. Also configure adequate independent token allowances; changing calls alone cannot overcome token/turn exhaustion. These example numbers are a test configuration, not a measured recommendation or new default.

## Ownership and counting

`executionBudget.js` holds a child-lifetime state on `session.budgetState`. `index.js` creates/retains a scope for runtime calls. The Electron `engine:chat` invocation creates one scope and passes it through `executeAgentTool`, `executeSpawnSubagent`, and legacy file/web facades. All children spawned by that invocation share it, including concurrent batches. Background children and later inbox/resume executions keep the same scope after the initiating parent invocation returns. A later parent chat invocation gets a new scope for its new children; it does not replace existing children’s scopes. Nested runtime calls with a runtime child as `parentSessionId` inherit that child's scope; nested tool spawning remains forbidden by the child allowlist.

Headless/runtime callers launching several sibling children must call `createParentRunBudget()` once and pass the same `budgetScope` to each run/start API. A chat session ID alone does not identify one parent invocation and is deliberately not a global budget key. A standalone direct run has its own scope. This state is in-memory; completed history metadata persists, but active jobs/ledgers are not restored after restart (unchanged lifecycle limitation).

A call counts immediately before an actual native child tool dispatch, file input read, or page fetch. Failed dispatched tools/reads/fetches count. Retrying an actual tool would count again; generation retries do not re-execute tools. Blocked validation, repetition, cancellation, or budget calls do not consume a dispatch slot, but are reported separately as blocked attempts. File-analysis metadata/directory traversal is not counted as independent model tool calls; each target-file open/read is. Web extraction fetches one logical page; redirect hops remain part of the existing guarded fetch. Parent spawn invocations are not additionally counted against the child aggregate (the existing parent tool limits still apply separately).

The tool gate synchronously compares/increments child and shared scope counters directly before dispatch. No await occurs between checking and claiming a slot, so concurrent main-process child promises cannot overshoot. A batch keeps every requested assistant call and appends a matching tool result for every executed or skipped entry. Further calls after exhaustion receive `[Tool skipped: <reason>]` and are never dispatched. Cancellation during a batch commits paired completed/unknown/skipped results before propagating abort, preventing a resumed tail from replaying completed work.

Canonical tool-name/parsed-argument signatures intercept a third identical attempt across a child lifetime. No results are cached or reused: even consecutive reads may observe different state. Repeated or forbidden calls do not open mutation tools; the existing read-only tool allowlist and permission checks remain independent. Parent repetition, failure-circuit, stream-loop and tool-ID safeguards remain intact.

## Model request and token accounting

Every actual generation dispatch counts as one request/turn, including failed HTTP/network requests, incomplete-answer continuation, finalization, and the existing local recovery's summary/retry. Scheduler queueing and tokenizer/capability probes do not count as generations. New provider budget plumbing charges at actual transport dispatch. `contextBudget.createContextGuardedFetch` accepts an optional tracker so existing recovery cannot hide requests inside one scheduler turn; callers without this tracker retain their original behavior. Phase 2 replaces the old child-local summary recovery with the shared Workspace candidate engine and an independent transcript adapter, described below. Recovery is driven outside the scheduler slot to avoid a capacity-one deadlock.

Before dispatch, the full prompt/tools must fit remaining input, and at least 256 completion tokens must remain independently. Each request's `max_tokens` is clamped to the remaining output budget, task-kind ceiling (or bounded adaptive escalation), and selected context window after prompt/output uncertainty margin. Local exact template/tokenizer counts are used when available; cloud metadata/descriptor/fallback windows and labeled conservative estimates otherwise apply. Measured input larger than the admission estimate stops further work with `input_budget`.

Tokens are reserved before dispatch. Reported prompt/input and completion/output aliases reconcile reservations; absent usage keeps the conservative reservation, never a free request. Unknown output retains the entire dispatched max_tokens. Failed requests also retain reservations. JSON and SSE replies reconcile once; file/web accumulate both attempts rather than returning only last-attempt usage. Usage fields represent sums of values actually reported, while `accounting` separately records input coverage, measured output, reserved output, request count, tool/blocked counts, shared aggregate snapshot and effective policy. Missing values are not advertised as measured zero. Persisted total_tokens stays unavailable when either side lacks complete measured coverage.

A provider can violate `max_tokens`; software cannot undo tokens already generated by a noncompliant backend. Reported overproduction stops with `provider_budget_violation`, and its requested tools are not executed. The implementation never silently sends a request larger than its output allowance. Input/context estimates remain estimates; precise real backend limits and adherence need live validation.

## Exhaustion and results

Investigation reserves its last configured request for tools-disabled reporting. Thus the default is at most seven ordinary investigation generations plus one reporting request, within eight total requests. Earlier tool/aggregate/no-progress exhaustion can trigger at most one tool-free finalization if there are useful tool findings and sufficient input/output/context/request allowance. Finalization is capped at 1024 output tokens and remaining resources. Providers that ignore tools-disabled reporting get paired skipped results; their requested tools never run and no second finalization is attempted. A confirmed failed context recovery returns partial evidence directly rather than initiating another compaction through finalization.

An incomplete length/reasoning-only response gets at most one investigation continuation, charged normally. Existing adaptive escalation doubles the request ceiling once when possible, bounded by context and remaining output. A response containing tool calls follows the normal dispatch path even if finish_reason is length; completed tools are not replayed. Empty/unusable output is never placeholder success. Visible length-truncated answers are explicit `incomplete_response` partials.

If reporting cannot run or fails, the result includes bounded excerpts of actual available tool/source evidence with provenance, or states that no usable findings were produced. It never invents task completion. File/web already request tool-free reports; their existing bounded second attempt is the only continuation, and input-call exhaustion reports the successfully read source subset.

Lifecycle statuses remain created/waiting/running/completed/interrupted/failed/cancelled, with **partial** added as a terminal incomplete outcome. Completed investigations remain continuable subject to the same lifetime ledger. Failed, cancelled and partial children cannot be resumed to evade limits. Interrupted children keep the ledger and paired context and may resume within remaining allowances.

| `stopReason` | Meaning |
| --- | --- |
| `completed` | Visible final answer without detected truncation/exhaustion |
| `tool_limit`, `aggregate_tool_limit`, `turn_limit` | Child/shared dispatch or total generation ceiling stopped work |
| `input_budget`, `output_budget` | Independent token allowance cannot fit another request |
| `context_exhausted` | Protected request/recovery cannot safely fit selected context |
| `compaction_failed` | Summary/checkpoint generation or preservation validation failed without changing active history |
| `no_progress` | Repeated equivalent tool attempts intercepted |
| `empty_response`, `malformed_response`, `incomplete_response` | No usable answer, invalid protocol/output, or visibly truncated answer |
| `provider_error`, `provider_budget_violation`, `runtime_error` | Provider failure, detected overproduction, or other execution failure |
| `cancelled`, `interrupted` | Existing cancellation/interrupt lifecycle |

Internal execution results add `outcome`, `stopReason`, and `accounting` to the existing output/usage contract. Foreground completed/partial results remain strings; partial strings begin `[Sub-agent partial: <reason>]`. No-findings failed results retain the existing foreground rejection contract with an explicit failed header/reason. `spawn_sub_agent` keeps its 1800-character parent result cap; the status header is first so truncation preserves it. Tool error settlement carries failed text to the parent. Background events expose actual status, result, reason and accounting. Sessions/executions/transcript inspection retain metadata; `subagent_runs.stop_reason` and `accounting_json` are added idempotently on database initialization. The existing bounded turns_json preview format is unchanged; it is not a raw replay log. Phase 2 adds separate raw/active/checkpoint persistence below. Transcript UI recognizes partial status and its reason; no new budget-usage UI was added.

## Phase 2: independent child-context compaction

Architecture and audited source locations:

- `compressionEngine.checkAndCompressContext` accepts a narrow `transcriptAdapter` branch without entering any parent DB/session lock. Primary-session calls keep their original DB snapshot, 75% stored-usage trigger, 65% target, ten protected message rows, branch/brief/evidence checks, archival and summary/checkpoint transaction. Casual sessions still skip Workspace checkpoint generation. Parent in-flight tool steps remain in the caller's paired live tail through `ipcHandlers` → `rebuildChatMessages` → `runMemoryChat`.
- `compactionCore.summarizeCandidates` is extracted from the actual Workspace selection/summarization loop. Both primary Workspace and children use it. `generateCheckpoint` shares the existing `taskCheckpoints.validateCheckpoint` and `renderCheckpointSection`; `main.js` and the child use the same extracted summary/checkpoint prompt constants. No parallel child summary/trimming algorithm remains in the old recovery module. `compactTranscript` adds adapter-based pressure/fit/commit orchestration around those shared functions.
- `subagents/contextRecovery.createChildContextAdapter` supplies the child's snapshot, complete protocol rounds, permanent instructions/task constraints, isolated raw evidence index, selected-provider generation, token measurement, version validation and own-record persistence. The validator's single injectable `messageExists` lookup is scoped to that child's raw IDs; primary Workspace retains its existing DB lookup. The child never uses the parent's session ID to compact, copies the parent's conversation, or writes parent messages/summaries/checkpoints.
- `agentLoop.runInvestigationExecution` checks the adapter before every ordinary or final reporting generation. Foreground, background and continuation paths share that loop. File/web children still use bounded throwaway contexts and do not acquire unnecessary compaction requests. Only investigation maintains a continuable tool conversation.

Pressure is full request input plus reserved next output and the existing uncertainty margin, divided by the resolved child context capacity. Descriptor/selected-cloud metadata/fallback resolution remains Phase 1's policy. Local prompts near pressure (rough ratio at least 60%) use existing `/props`/template/tokenizer measurement when available; comfortably short tasks avoid extra probes. Local server-reported limits can reduce the effective adapter window. Cloud uses explicitly labeled byte-based approximation. Exact-measured pressure triggers at **78%**; estimated pressure triggers at **75%**. These are conservative initial test values, not verified universal thresholds. There is no fixed-turn interval and no new user setting. The existing global/selected-model `compactionEnabled` setting is honoured without consulting the parent session.

Child candidates are whole completed assistant/tool rounds; the newest two complete rounds remain verbatim in active context. All permanent system instructions and original/follow-up user task constraints stay pinned. The original task is also retained as an authoritative checkpoint requirement. The engine refuses in-flight, duplicate-ID, unmatched or malformed protocol pairs before provider dispatch. It merges prior summary and checkpoint state, validates references against actual raw tool outcomes, preserves earlier checkpoint entries, and refuses if shared size caps would clear or trim essential retained state. This avoids silently erasing older discoveries in later compactions; it may conservatively stop a child whose required state has become too large. Structural/evidence-reference validation does not prove every model-authored factual sentence semantically correct; source evidence remains inspectable.

The child performs at most one summary request (up to 512 output tokens) and one structured checkpoint request (up to 1024), each through its **same scheduler, model, saved provider and Phase 1 ledger**. Tools are absent/disabled; incomplete/tool-bearing drafts fail. Before starting these requests, it requires at least three request slots and 512+1024+256 remaining output allowance, so the two drafts leave a resumed/reporting request possible. Actual dispatch still clamps/charges/reconciles each request. After compaction, the loop rechecks the reporting reserve and shared aggregate exhaustion; another child consuming the aggregate during compaction cannot create over-budget work.

Before commit, the engine measures the prospective full request and output reserve, requires actual safe fit, and requires savings of at least max(128 input tokens, 10% of prior input). Failed generation, malformed checkpoint, excessive protected floor, inadequate savings, budget exhaustion, cancellation or changed transcript/model/version cannot archive or replace active history. A failed compaction does not trigger another summary through finalization. Original identity/model/provider/root/read-only permission/tool schema state stays with the runtime; reconstruction invokes no tool executors.

Confirmed overflow uses **one compact-and-retry** at most for that model request, after the inference scheduler has released its lane. This is necessary because queueing a summary while holding the local capacity-one slot would deadlock. `contextBudget` marks confirmed backend overflow; local provider fixtures and cloud transport classify only known context-size codes/shapes. Cloud error bodies are classified in memory and not logged, persisted, or attached to returned errors. Generic HTTP/auth/quota failures are not treated as context overflow. A repeated overflow or a non-compressible protected tail returns the Phase 1 partial/failure context stop. The retry resends compacted messages; it never dispatches tools again. Primary-session guarded-fetch recovery remains unchanged apart from diagnostic classification.

Oversized native results are recorded **before** model-context projection. `trimToolResult` leaves small outputs untouched; the active-context ceiling is min(12000 characters, 12% of window × 3), with a 1200-character minimum. Large file-result JSON keeps path/line-count metadata and explicit trimming metadata; text uses safe Unicode head/tail and task/error/value excerpts with an omission notice. Existing native file/web caps still apply upstream, so raw means the complete result actually returned by the native tool, not unlimited underlying file/page contents. Checkpoint requests also bound their newest-first evidence payload (Workspace's 12k character ceiling, additionally window-scaled) and state the omitted count; validation retains the full raw evidence index and earlier validated checkpoint. These reductions do not change actual tool execution outcomes or reuse cached data.

Persistence is now explicit:

| Storage | Purpose |
| --- | --- |
| `session.rawContext` / `subagent_runs.raw_turns_json` | Original child instructions, user messages, assistant calls/results and final responses, with child-local stable source IDs; never replaced by a summary |
| `session.context` / `subagent_runs.context_json` | Current protocol-valid, trimmed/compacted projection used by subsequent child model requests |
| `session.compactionState` / `subagent_runs.compaction_json` | Versioned current summary/checkpoint and compaction event metadata: pressure method/window/reserve, before/after counts, archived raw IDs and before/after ledger snapshots |
| existing `turns_json` | Bounded raw-history preview for the existing inspection contract; separate `activeTurns` preview exposes the model context |

Raw and active/checkpoint state are upserted together in the child's own existing history row at safe boundaries (including before/after compaction), not stored in parent messages. New nullable columns are added idempotently; old rows retain preview fallback. Full raw history is available for inspection, while IPC previews remain capped. Persistence stays best-effort if storage is unavailable; in-memory originals still survive a failed write. Active jobs are still not resumed automatically after application restart. No Phase 3 UI/dashboard or delegation guidance was added.

Phase 1's aggregate 40-call ceiling is unchanged and still counts tool dispatches, not summary requests. Every summary/checkpoint/retry consumes child request/input/output budget; compaction is never a budget reset. The eight-request Automatic investigation limit can therefore permit only a small number of compactions before reporting. This remains a deliberate safe bound pending live evaluation, not proof that the 50-call candidate or a higher default is optimal. The two compaction-enabling Phase 1 adjustments are: defer guarded-transport input/context admission until its actual tokenizer/fallback measurement (to avoid rejecting an exactly fitting compacted prompt prematurely), and recheck reporting/aggregate state after compaction requests. No other Phase 1 policy was expanded.

## Parent delegation and activity display (Phase 3)

The parent system protocol now requests concrete bounded assignments with explicit sources, exclusions and acceptance criteria. Sibling tasks should not overlap. Ask for concise evidence first (file/line or URL), then uncertainty and unfinished work. Reuse partial findings and narrow subsequent work to unresolved questions. Extra local children may share a serialized GPU lane; delegation is context isolation, not a promise of speedup. The tool schema carries the same assignment/output guidance. This is prompt guidance, not a scheduler or a guarantee of model adherence.

The activity modal keeps the runtime lifecycle status and typed stop reason. Completed output is labelled Final answer; partial output is Partial findings; cancelled, interrupted and failed output is Returned output. Execution count is distinct from model request count. Accounting shows effective frozen per-child tool/request/token limits alongside observed consumption, blocked attempts, and the shared parent-run tool snapshot. The shared snapshot is captured at settlement and may lag later sibling work; it is not a continuously recomputed aggregate meter. During execution accounting may be unavailable or reflect the preceding settlement. Old history without accounting explicitly shows unavailable limits/coverage.

Input coverage is measured, estimated, mixed, or unavailable. Output separates provider-measured tokens from conservative reserved tokens, with coverage labelled explicitly. A reservation is an allowance charged when provider usage is absent, not a measured token count. Missing reported token sides display unavailable rather than zero. Reporting attempts and any finalization stop reason are shown separately from the primary reason the investigation stopped. Full totals are shown only when the existing runtime supplies them. Settings explain that the last investigation request is reserved for reporting and that compaction/retries consume the same total allowance.

The 10 tool-call / 8 total request defaults, including the reporting reserve, and 40 shared tool-call ceiling remain unchanged: inspection and deterministic tests supplied no tuning evidence. Compaction's two draft requests plus retained next-request allowance compete with investigation/reporting within eight requests. Whether those defaults are useful for real long tasks remains a Phase 4 decision. See `subagent-phase3.md` and `subagent-phase3-evidence.json` for this phase's verification and handoff.
